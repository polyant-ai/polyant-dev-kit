# Authoring & loading Polyant tools/plugins

## The contract

A plugin is a directory of `*.tool.ts` / `*.hook.ts` files authored against
`@polyant-ai/plugin-sdk`. Only two things cross the boundary into the engine:
**data** (your Zod schema, serialized to JSON Schema at module load, inside your
own realm) and a **function** (`execute` / `handler`). Never a live Zod object,
never a shared singleton. That is what lets your plugin and the engine each
resolve their own copy of the SDK, of `zod`, and of `ai` without breaking.

### Tools

`export default defineTool({ name, description, category?, requiredEnv?,
requiredSecrets?, inputExamples?, harness?, parameters, execute })`.

- `parameters` is a **static** Zod schema — it may not read `ctx`.
- `execute(input, ctx)` holds the business logic.
- `harness: true` hides the tool from the admin panel and from the agent's tool
  selection: it is equipped only by a runtime that asks for its category. That is how
  a tool exists for one execution surface without being enableable everywhere — it
  bypasses the agent's tool list entirely, so it is also the one kind of tool nobody
  can turn off. Leave it unset unless you are shipping the surface too.
- `ctx.secrets` is `Record<string, string> | undefined`, **scoped to the keys you
  declared in `requiredSecrets`**. An undeclared key is simply absent: to read a
  secret you must declare it. This is enforced by the engine, not by convention.
- `requiredSecrets` accepts a bare string (shorthand for `{ key, type: "text" }`,
  masked) or a full spec `{ key, type: "text" | "select", label?, description?,
  choices?, optional?, sensitive? }`. `type: "select"` requires non-empty
  `choices`. A readable config value like a base URL wants `sensitive: false`, so
  the admin panel shows it in clear.
- `ctx.state`, `ctx.conversation` and `ctx.oauth` are **optional** on the type —
  older engines may not provide them. Guard for undefined. `ctx.oauth` carries
  `requireToken(provider)` and `connectResult(provider)`.
- **Enterprise:** `ctx.knowledge` is the agent's own knowledge base, and it is
  **present only when the agent grants access**: its presence is the read grant, and `ctx.knowledge.level`
  (`read` / `write` / `manage`) says how far the tool may go. Declare the minimum with
  `requiredKnowledge` on `defineTool` and the engine does not equip the tool at all
  on an agent that grants less, the same way it prunes a tool whose secrets are unset.
  A write only updates documents this plugin wrote, until the level is `manage`.
- `ctx.artifacts` hands generated bytes from one tool to another in the same
  conversation — one plugin renders a PDF, another uploads it — since two plugins
  cannot import each other's module. `put` returns a handle for the model to pass
  on; `take` consumes it once and answers `null` when it is unknown, taken, expired
  or from another conversation. Entries are short-lived and size-capped, and `put`
  throws when a limit is reached. **Always `await` both**: in Enterprise dev mode each call
  is a round trip to the engine. Anything that must outlive the turn belongs in durable
  storage. It needs SDK `v1.9.0`, and it is the only `ctx` member the type marks as
  always present, so a fake context in a test has to provide it.
- The rest of `ctx` — `instanceId`, `audit`, `conversationId?`, `attachments?`,
  `apiKeys?`, `provider?` — is there too. Read the SDK's context type rather than
  this list when you need one of them.

### Hooks

A hook is deterministic lifecycle code, bound to one of four conversation
events — `conversation_start`, `message_received`, `response_generated`,
`response_sent` — via the agent's configuration. Unlike a tool, a hook is
never LLM-invoked and never appears in the tool catalog.

`export default defineHook({ name, description, requiredSecrets?,
mutatesResponse?, handler })`.

**A hook does not declare its own event.** There is no `event` field in the spec:
the event→function binding lives in the agent's configuration. Your handler reads
`ctx.event` and branches if it must behave differently per event.

`ctx` gives you `event`, the server-built `payload`, read-only `conversation`,
read+write `state`, scoped `secrets`, `instance` metadata, and `ai.chat(...)` bound
to the agent's configured model. Unlike a tool, `conversation` and `secrets` are
**required** here — a hook-capable engine always builds both.

Returning nothing means observe-only. Returning a control object influences the turn:

| Return | When it is honored |
|---|---|
| `halt: { message, persist? }` | pre-LLM events only — skips the LLM and delivers `message` as the reply. `persist` defaults to `true`; see below |
| `injectContext: string` | pre-LLM only — appended as one-shot context to this turn, **truncated at 4000 characters** |
| `replaceResponse: { message }` | `response_generated` only. Honored on a non-streamed turn even without `mutatesResponse: true` — but declare the flag anyway, because that is what *makes* the turn non-streamed |
| `regenerate: { reason? }` | `response_generated` only, **hard-gated** on `mutatesResponse: true` — a replay costs up to 6x a normal turn |

`mutatesResponse: true` makes the engine run the turn non-streamed, so a
`replaceResponse` is never too late. The gate is about whether the return is
**honored**, not whether it is logged: without the flag, `replaceResponse` on
a streamed turn is skipped and warned (the tokens are already on the wire),
and `regenerate` is likewise never honored and warned (the flag is what earns
a hook the 6x replay cost) — neither one is silently dropped.

**`halt` can leave no trace of the turn.** `halt: { message, persist: false }`
delivers the message and writes nothing — no user or assistant row, no latency trace,
no conversation-state flush, no summary or memory work. The exchange stays out of the
model's history, while the hook execution itself is still recorded, so the turn is
auditable even though it is invisible to the next one. That is what a command-style
hook wants (`RESET`, `/help`): the command and its answer should not become context
the model reasons about later. The conversational path honours it; the
supervise-direct room and webhook paths ignore it. It needs SDK `v1.5.0` or newer.

**A hook missing a secret does not run.** If a key it declares (and did not mark
`optional`) has no value configured for the agent, the handler is never invoked and
the misconfiguration is audited. The turn proceeds as if the hook were not wired —
so a hook that "does nothing" is a configuration question before it is a code one.

**Caveat on `regenerate`:** it replays the entire turn, tools included. A
non-idempotent tool can fire up to six times. Enable a regenerating hook only
where the turn is side-effect-free or every tool it calls is idempotent.

### Tool example

```ts
import { defineTool } from "@polyant-ai/plugin-sdk";
import { z } from "zod";

export default defineTool({
  name: "myTool",
  description: "…",
  category: "…",
  requiredSecrets: ["some_api_key"],
  parameters: z.object({
    query: z.string(),
    limit: z.number().nullable(),
  }),
  execute: async (input, ctx) => {
    const apiKey = ctx.secrets?.some_api_key;
    if (!apiKey) return { error: "missing some_api_key secret" };
    const limit = input.limit ?? 10;
    // … call the API with input.query, capped at `limit`
    return { status: "ok", result: `searched "${input.query}" (limit ${limit})` };
  },
});
```

### Hook example

```ts
import { defineHook } from "@polyant-ai/plugin-sdk";

export default defineHook({
  name: "myHook",
  description: "…",
  mutatesResponse: true,
  handler: async (ctx) => {
    if (ctx.event !== "response_generated") return; // observe-only elsewhere
    if (!ctx.payload.response) return; // response is optional on the type
    const looksCorrupted = ctx.payload.response.text.includes("�");
    if (looksCorrupted && ctx.payload.response.regenerationCount < 2) {
      return { regenerate: { reason: "corrupted output" } };
    }
  },
});
```

### Schema rules (OpenAI strict-mode compatible)

OpenAI's strict function-calling mode rejects any tool whose JSON Schema doesn't
meet this shape — the tool fails before it is ever invoked. This is the single
home for the banlist (see `tool-design` for *why* it matters to the tool's design):

| Banned | Why | Instead |
|---|---|---|
| `.optional()` / `.default(...)` | the property is omitted from `required` | `.nullable()`, apply the default in `execute` |
| `.url()` / `.email()` / `.uuid()` / `.datetime()` | emit a `format` keyword that is not accepted | validate the shape at runtime in `execute` and return `{ error }` |
| `z.record(z.unknown())` / `z.record(z.any())` | produces unbounded `additionalProperties` | take a `z.string()` and `JSON.parse` it in `execute`. A typed map (`z.record(z.string(), z.string())`) is fine |

`.transform()` / `.refine()` / `.superRefine()` / `.preprocess()` are **not**
banned by strict mode — the JSON Schema is derived from the pre-transform shape,
so none of these affect it. But the engine validates a tool call against that
static schema (not against your live Zod object) and hands `execute` the raw,
untransformed input — so a `.transform()`/`.refine()` inside `parameters` never
actually runs; it's dead code, not a rejected tool. Put cross-field coalescing
and validation in `execute` instead, where it can see both fields and return
`{ error }` instead of throwing.

## Two ways onto an instance

A plugin reaches a running instance in one of two forms, and they do not accept the
same plugins. The first works on both editions; the marketplace is **Enterprise**.

**Baked into the image.** The plugin directory is on the engine's disk: in the
engine's plugin directory at build time, or listed in `PLUGIN_DIRS`
(comma-separated absolute paths). A plugin file resolves its imports from its
**realpath**, so the directory needs its **own** `node_modules`: run `npm install`
there with the SDK as a git dependency. **Never a symlink.** The loader resolves the
symlink to its realpath and then cannot find the dependencies you expected. This is
the only form that may ask the image for system packages (see `system` below), and
it is a decision of whoever builds and runs the instance.

**Installed from the marketplace — Enterprise.** The plugin is published as a signed runtime
bundle — its tool and hook definitions as data, and one ESM file into which every
npm dependency is bundled — and an Organization Admin installs a release from
Organization settings → Plugins, without an image rebuild. A bundle runs in a worker
thread, never in the engine's main thread. It **cannot declare a `system` block**:
native addons, binaries, install scripts and image packages are refused when the
release is published. Publication goes through the marketplace's own review; the
`namespace` is permanent once published, and every release needs a new `version`.

### `plugin.json`

Each plugin carries one: `name`, `version`, `engine` (a semver range), `toolsDir`
(default `tools`), `hooksDir` (default `hooks`), `namespace` (default `name`),
optional `displayName` and `description` for how the panel presents it, and
`oauthProviders` (below). Every tool loads as `<namespace>:<name>`. Two plugins
resolving to the same final name fail the boot loudly.

An image-baked plugin may add `system`, read at **build time** and never at runtime:

```json
"system": {
  "apk": ["chromium"],
  "npmGlobal": [],
  "env": { "PUPPETEER_EXECUTABLE_PATH": "/usr/bin/chromium-browser" }
}
```

`apk` lists Alpine packages for the runtime image, `npmGlobal` npm packages installed
globally for the executables they put on `PATH`, and `env` variables pointing at
them. The image installs the union of every included plugin's block; a declared
variable is a default the container environment can override, and two plugins
declaring one variable with different values fail the build. A plugin whose binary
is missing fails on the tool call, never at boot — so an image built without your
plugin's block does not carry what it needs, and nothing says so until a call.

A plugin whose `engine` range excludes the running engine is skipped with a warning
and boot continues; so is an individual tool or hook file that throws while loading.
Neither stops the instance, so **confirm the tool appears** rather than reading a
successful boot as proof. The name the model is given sanitises the separator
(`<namespace>__<name>`, because some providers reject `:`) — if a prompt has to
name a tool, that is the form it will see.

Tools that used to be core and now ship as plugins carry their plugin's namespace.
Since engine 1.2.0 the HubSpot tools are `hubspot:contact`, `hubspot:note`,
`hubspot:deal` and their siblings (formerly `hubspotContact`, `hubspotNote`, …), and
Markdown-to-PDF is `extra:markdownToPdf`. An agent's enablement moved with the rename,
but a prompt or a skill that names the old flat name now names nothing: search them
when you upgrade.

Your plugin references `@polyant-ai/plugin-sdk` as a git dependency **pinned to a
tag** (e.g. `git+https://github.com/polyant-ai/polyant-sdk.git#v1.9.0`), not a
branch — so an SDK release never silently changes your plugin's behaviour
underneath you. Pin to the tag the target engine itself depends on — engine 1.2.0
depends on `v1.9.0` — because an SDK newer than the engine can carry fields the
engine does not read yet.

### Being on disk is not being available — on Enterprise

On OSS a plugin the engine loaded is available to every agent: enable its tools and
set their secrets. On **Enterprise**, availability is per-organization, and how an
organization comes to hold a plugin depends on its form:

- a **marketplace** plugin is installed by an Organization Admin or Owner (the
  `org.plugin:manage` permission), who also picks the version, updates and rolls
  back. A Platform Admin can deny a marketplace plugin to one organization, which
  hides it from that organization's catalogue and removes it if it was installed,
  can block a release for the whole installation, and a publisher can revoke one;
  none of these can be undone from inside the organization;
- an **image-baked** plugin is granted to the organization by a Platform Admin.

Without that, the plugin is invisible in the management surfaces and its tools are
withheld at runtime — the agent simply never sees them, which looks exactly like a
plugin that failed to load. On hosted Polyant both the image and the platform
decisions belong to whoever runs the instance: ask them.

Holding the plugin still is not availability in a **workspace**: the workspace
carries its own assignment, and an agent sees the intersection. Installing does not
assign. `workspace plugins list <workspace>` lists only the plugins the organization
holds, with an ASSIGNED column for the workspace's half — an ungranted plugin is
absent rather than shown as ungranted, so a name missing there may be ungranted or
not installed at all. Assigning a plugin the organization does not hold is refused
instead of being written as a row that changes nothing, and so is assigning one the
engine reports unavailable. After the assignment, the agent still needs the tool
enabled and its secrets set.

## A plugin is not the only way to get a tool

An agent can also equip tools from an external **Model Context Protocol** server.
Before you write a plugin, ask whether the capability already exists as one: an MCP
server is configuration, a plugin is code you then have to place on the instance's
disk or publish — and, on Enterprise, have installed or granted. The plugin is the right answer when the tool must own a
decision, read the agent's own secrets or state, or gate a turn — see `tool-design`;
the MCP server is the right answer when a third party already exposes the capability
and you only need to reach it.

**It is configured per agent**, as a list of servers, each with a slug, a URL, an
enabled flag and one of three auth modes:

| Mode | Carries | Use it for |
|---|---|---|
| `none` | nothing — a token sent by mistake is a `400` | a public server, or one behind network isolation |
| `static` | a bearer token, or a named header and its value | a server with a long-lived credential |
| `oauth` | OAuth 2.1, optionally with a static client or dynamic registration | a server that authorizes per user |

Every mode also accepts an **`allowList`**: the remote tool names the agent may
actually call. Without it the agent equips everything the server offers, and what a
server offers can change without you. Set it, and treat a remote server's catalogue
as untrusted input rather than a fixed contract.

Credentials are encrypted at rest and never returned by the API, so a read gives you
the shape and not the value — the same rule as an agent's secrets.

### It degrades silently, per turn

The tool list is rebuilt on every turn by dialling each enabled server, and a server
that does not answer inside the platform's MCP connect timeout (10 seconds by
default; a Platform Admin sets it in Settings → General) is **skipped with a
warning**. The turn proceeds with fewer tools; nothing tells the model that a
capability it had five minutes ago is gone, and nothing tells you either unless you
read the log. So an agent that "sometimes forgets how to do X" is an MCP question
before it is a prompt question.

Three more ways a server contributes nothing:

- **The URL is re-checked at connect time**, resolved addresses included, not just
  when you saved it. A hostname repointed at an internal address after the fact is
  rejected on the spot, and the server is skipped like an unreachable one.
- **An `oauth` server is skipped entirely on non-conversational paths.** A room, a
  webhook or a scheduled run mints a fresh conversation each cycle and has no user
  present to open an authorize link, so the engine does not try. An agent driven by a
  webhook does not have its OAuth MCP tools — plan the capability accordingly.
- **A name collision loses the second tool.** Every remote tool is equipped as
  `mcp__<server>__<tool>` (the `:` separator sanitised, the whole name capped at 128
  characters); two that sanitise to the same string keep the first and warn about the
  second. That is also the form a prompt would have to write if it names one.

`agent mcp` reaches all of it. A server's configuration, credential included,
arrives as a file or stdin, never a flag:

```bash
npm run polyant -- agent mcp show <slug>
npm run polyant -- agent mcp set <slug> <server> --file server.json
npm run polyant -- agent mcp test <slug> --file server.json
```

`test` dials a candidate server and reports what it offers. Reach for it before you
blame the agent: a tool the agent "will not use" is usually a tool it was never
handed.

## OAuth providers (for OAuth tools)

A plugin whose tools use `ctx.oauth` declares the providers they need under
`oauthProviders` in `plugin.json` (`{ name, authorizeUrl, tokenUrl, scope,
extraAuthorizeParams?, pkce? }`) — the engine registers them into its OAuth
broker at boot, so shipping a provider needs no engine change. The tool then
calls `ctx.oauth.requireToken("<name>")` and declares client credentials via
`oauthRequiredSecrets("<name>")`. Provider `name` is a flat global key (secret
keys, token vault, `/oauth/<name>/callback`) — not namespaced; a same-name
divergent definition across two plugins fails the boot (use distinct names for
divergent scopes). `OAuthProviderSpec` is exported from the SDK as optional typing.

## Verify

From your plugin directory:

    npm run typecheck
    npm test

Then point your Polyant instance at the plugin with `PLUGIN_DIRS` and confirm the tool
appears in the agent's Tools list. On Enterprise, also have it granted to your
organization — or install a published release from the marketplace — and assign it
to the workspace. A tool absent from that list is a load failure or, on Enterprise, a
missing grant, installation or workspace assignment — all of them are silent.
